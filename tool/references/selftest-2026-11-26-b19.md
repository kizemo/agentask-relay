## 1. B19-a 台账自描述：`LEDGER_CHAIN`

### 问题

B18 把触顶判据行改成带 `stages=` / `all_done=` 之后，人（和会话）仍然得**先跑一次启动器**才能看到链走到哪一步：
`relay-ledger.ps1 -Action status` 只印 `LEDGER_STATE ... status=running current_stage=1 max_stages=2 stages=1 sha256=...`，
其中 `stages=1` 是**阶段条数**，不是「哪些阶段什么状态」。想知道「是不是所有阶段都 done」只能去读 `docs\relay.json` 原文。

### 做法：status 输出第二行，词汇与启动器 FAIL 行对齐

`tool\templates\relay-ledger.ps1` 的 `status` 分支在 `LEDGER_STATE` 之后、`exit 0` 之前新增一行：

```
LEDGER_CHAIN current_stage=<n|空> max_stages=<m|空> cap_reached=<true|false|unknown> stages=<id:status,...|none> all_done=<true|false|unknown> open_stages=<n|none>
```

字段语义（全部来自台账原文，不猜）：

| 字段 | 取值 | 说明 |
|---|---|---|
| `current_stage` / `max_stages` | 原样 | 缺失就印空，不补 0 |
| `cap_reached` | `true` / `false` / `unknown` | 两个数都能解析才比较；**缺一个就是 `unknown`，不写 `false`** —— 在无法比较的台账上写 `false` 等于宣称「还有余量」 |
| `stages` | `1:done,2:pending` / `none` | 逐阶段的 `id:status` 列表；无阶段记录是 `none` |
| `all_done` | `true` / `false` / `unknown` | 每条阶段记录都 `done` 才 `true`；无阶段记录是 `unknown`（不是 `false`，完成性无法证明） |
| `open_stages` | 数字 / `none` | 未 done 的阶段数；无阶段记录是 `none` 而非 `0` |

实测五形态（自测 case 25 的夹具，逐字取自日志）：

```
LEDGER_CHAIN current_stage=2 max_stages=2 cap_reached=true  stages=1:done,2:done       all_done=true    open_stages=0
LEDGER_CHAIN current_stage=2 max_stages=2 cap_reached=true  stages=1:done,2:pending    all_done=false   open_stages=1
LEDGER_CHAIN current_stage=2 max_stages=2 cap_reached=true  stages=none                all_done=unknown open_stages=none
LEDGER_CHAIN current_stage=1 max_stages=2 cap_reached=false stages=1:running,2:pending all_done=false   open_stages=2
LEDGER_CHAIN current_stage=  max_stages=  cap_reached=unknown stages=1:done            all_done=true    open_stages=0
```

### 关键设计：两台独立实现，不许互相抄

启动器算 `stages=` / `all_done=`（`start-relay.ps1` 触顶分支 `176-190`），台账算 `LEDGER_CHAIN`
（`relay-ledger.ps1` `186-212`）—— 这两处是**各自独立写的代码**，源码里也有注释写明「故意分开算」。
自测把同一份台账喂给两边，逐字段比对：任何一边漂移都会红，而不是被另一边悄悄覆盖过去。

`stages=` 在两行里**同名不同义**（`LEDGER_STATE stages=1` 是条数，`LEDGER_CHAIN stages=1:done,2:done` 是列表）。
自测专门有一条 `chain_status_keeps_the_stage_count_distinct` 钉住这一点，防止后人「统一命名」时把语义揉平。

## 2. B19-b 受管自动收尾：`-AutoFinalize`

### 为什么默认关

`FAIL reason=chain_at_stage_cap ... all_done=true` 之后的下一步动作是**写台账**。写台账是整条链里唯一会改
权威状态的动作，B18 才刚把它从一个说假话的 HINT 里救出来。所以这一批**不**让启动器默认代写：
必须显式传 `-AutoFinalize`。

### 守卫与流程

`tool\templates\start-relay.ps1` `199-254`，进入条件是 `$AutoFinalize -and $allDoneState -eq 'true'`
（**且**已经走到触顶分支 —— 这段代码本身就在该分支里）：

1. `-DryRun` ⇒ 只印 `DRYRUN skip=auto_finalize reason=every_declared_stage_is_done_but_a_dry_run_never_writes`，不写；
2. 取 `relay-ledger.ps1 -Action status`，从 `LEDGER_STATE` 行里抠 `sha256=<64hex>`（CAS 前置值）；
3. 在**仓库外**（`%TEMP%\relay-autofinalize-<guid>.json`）写一行 patch `{"set_status":"done"}`，
   调 `relay-ledger.ps1 -Action commit -ExpectSha256 <sha> -Patch <tmp>` —— 锁、CAS、只追加、写后回读全在闸门里；
   patch 用完 `finally` 删除（它是一次性输入，不该留在仓库里让人当成产物）；
4. 再取一次 `-Action status` 回读，确认 ` status=done `；
5. 成功打印 `AUTO_FINALIZED status=done before=<64hex> after=<64hex> path=<ledger>`，
   并换掉 HINT：`HINT=chain_closed_by_auto_finalize: ...`（告诉读者重跑会得 `chain_exhausted`，要接着干得开新链）。

失败路径只有一条：任何一步异常 ⇒ `WARN auto_finalize=failed reason=<异常消息，空白折成下划线>`，
**台账一个字节不动**，然后落到分支末尾共享的 `exit 3`。

### 三条刻意选择

- **退码仍是 3**：本次调用没有起链。把自动收尾成功当成 0 会让「起链成功」与「没起链但顺手关了个环」混为一谈。
- **不补第二条 `FAIL`**：成功时若再印一条 `FAIL reason=chain_exhausted`，读者会以为清链失败了。只换 HINT，不加 reason。
- **分支内不写裸 `exit 3`**：落到分支末尾那一个共享 `exit 3`（`:255`），B18 变异探针的
  `(?m)^    exit 3\r?$` 锚点因此仍然成立。

### 一条已知的「只靠启动器守」的风险（B20 候选）

`relay-ledger.ps1` 的 `set_status` 只拒 `running`（`:309-313`），所以「还有阶段没跑就提交 `set_status=done`」
在**台账侧不被拒**。当前唯一保护是启动器的 `all_done=true` 守卫 —— 变异体 1 正是把守卫拿掉看它变红。
B19 **故意不**给台账加这条校验：`set_status` 是人工裁决后手动收尾的合法入口（阶段被砍、目标变更），
把校验塞进闸门会切断这条路。要收这个口子属于策略变更，留 B20 讨论。

## 3. B19-c 自测：case 25 / case 26（+45 条）

插入位置在 case 24 之后、`# --- verdict ---` 之前（套件末尾）。

### case 25 —— `chain_status_*`（+22）

夹具 `repo-chain-status`，五种台账形态各跑一次真实 `relay-ledger.ps1 -Action status`：

| 形态 | 断言点 |
|---|---|
| `all_done` | 读得到 / 形状逐字段 / `LEDGER_STATE` 仍在 / `stages=` 与启动器一致 / `all_done=` 与启动器一致 |
| `open_stage` | 同上（这是最容易被写成 `all_done=true` 的形态） |
| `no_records` | 同上，且必须是 `all_done=unknown` + `open_stages=none` |
| `below_cap` | `cap_reached=false`，不触顶 |
| `no_numbers` | `current_stage` / `max_stages` 空 ⇒ `cap_reached=unknown`（不是 `false`） |

另加 `chain_status_keeps_the_stage_count_distinct`：同一份输出里 `LEDGER_STATE stages=<数字>` 与
`LEDGER_CHAIN stages=<id:status>` 必须**同时**出现且互不串味。

> 交叉一致断言是本批的重点：`chain_status_*_agrees_with_launcher_*` 让启动器与台账两处独立实现互校。
> 变异体 2 就是把这台「独立实现」拉平成常量，看这几条会不会红。

### case 26 —— `auto_finalize_*`（+23）

夹具 `repo-auto-finalize`，六个子场景串行：

| 场景 | 断言 |
|---|---|
| s1 还有阶段没跑 + `-AutoFinalize` | 不收尾（`status=running`）/ 不印 WARN / 仍 `exit=3` |
| s2 全 done + `-AutoFinalize -DryRun` | 印 `DRYRUN skip=auto_finalize` / 台账不动 / `exit=3` |
| s3 全 done + 不传开关 | 台账仍是 `running` / 仍印触顶 FAIL |
| s4 全 done + 新鲜 `.ledger.lock` | `WARN auto_finalize=failed` 且含 `writer_lock_timeout` / 台账不动 / **锁未被夺走** / `exit=3` |
| s5 删锁后重跑 | `AUTO_FINALIZED` / 回读 `status=done` / `before=` 与 `after=` 都是 64 hex / HINT 已换 / **没有**第二条 reason / `exit=3` |
| s6 再重跑 | `FAIL reason=chain_exhausted` 且**不再**出现 `AUTO_FINALIZED` |

s4 是本批最要紧的一条：锁文件写成 `pid=<活进程> host=<host> taken_at=<ISO>` 的新鲜文件，
`Enter-WriterLock` 因此不会判 stale 接管，commit 撞 `writer_lock_timeout`（exit 4）。
**这证明了「写确实经过闸门」** —— 如果哪天有人把自动收尾改成裸写台账，s4 会立刻变绿/变红不一致。

## 8. 本轮工具坑（新增，接 B18 的 32）

33. **`(Get-Process -Id $PID).Path` 在自己人跑自己的场景里指向的是「子宿主」**：自动收尾需要再起三次
    `relay-ledger.ps1` 子进程（status → commit → status），而台账闸门是用 `exit` 报结论的，**不能在同一进程里调**。
    用 `$PID` 反查当前宿主的可执行文件是可行形状 —— 但把它写进用例时要清楚：`selftest.ps1` 的 `Run`
    helper 本来就是另起子 pwsh，所以那里解析到的是子宿主，不是外层。只要路径可执行，行为一致。
34. **`cap_reached` 这类三态字段不能用 `false` 当「不知道」**：缺字段时写 `false` 会被下游读成「还有余量」，
    和 `all_done=unknown` 是同一个道理的镜像 —— 三态字段宁可多一个 `unknown`，也不要靠 `false` 兜底。
35. **自测里要让「写闸门」真的亮红灯，锁文件必须是「新鲜的」**：`Enter-WriterLock` 按 `LastWriteTime`
    超 `-LockStaleSeconds` 才接管，随手写个空锁文件会被判 stale 直接夺走，于是 commit 成功、用例反而绿。
    正确做法是写 `pid=<活着的进程> host=... taken_at=<ISO>` 并断言锁文件事后仍在。
36. **`Set-Location` 与写操作放同一条内联命令会被本地安全策略拒**（`write/delete targets cannot be verified
    safely after a command working directory change`）：跨目录改文件一律用全绝对路径、不切目录，
    或写成 `.ps1` 再执行。
37. **变异探针的结构行存活断言必须按目标文件定制**：两个变异体改的是不同文件（启动器 / 台账），
    同一个「`exit 3` 行必须还在」的锚点对台账根本不成立，探针会自伤抛 `mutant_lost_the_exit_line`，
    第二个体压根没跑。改成 `-MustKeep` 参数、按目标文件传各自的结构锚点才跑得完。
    另一条：**期望红名单必须从源码推、不许拿观测值拟合** —— 观测到 2 条红就写 2 条红，等于把判据
    降级成「复述现象」。正确做法是回源码解释第三条为何天然盲（守卫被拿掉后写台账成功、根本不走 WARN 路径），
    再把它转成显式的「必须保持绿」断言，这样变异一旦扩散到不该红的用例也会被抓到。
