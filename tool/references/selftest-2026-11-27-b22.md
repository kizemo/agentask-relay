# B22 小结：Claude Code 项目登记册被验证夹具污染 —— 根因、装置修复 `-EphemeralWorkspace`、门禁收尾

本批处理一个现场问题：**在 cc-haha（Claude Code 桌面端）里用 relay-port 接力，侧栏多出一堆用户从没要求过的
「新项目」，链子看起来「没进原来的项目」。** 结论先给：

> **不是 cc-haha 的 bug，也不是链接接错了项目。是「真链验证用的临时夹具」在 Claude Code 的用户级项目登记册里
> 留下了条目，而桌面端正是把这个目录当项目列表渲染的。** 责任在装置侧（relay-port 的验证方式与产物清理），
> 不在桌面端。

---

## 1. 根因：Claude Code 按 cwd 分项目，登记册是用户级的

Claude Code 把每个会话按 **cwd** 归档到 `<profile>\.claude\projects\<mangled-cwd>\`，
`mangled-cwd` = 路径里所有非字母数字字符换成 `-`。

桌面端（cc-haha）**没有自己的 projects 表**（`cc-haha\db\index-v1.sqlite` 里没有 `projects` 表），
它直接扫描那个目录，把每个目录当成一个「项目」显示。于是：

- **真实项目跑链** → 出现该项目的目录 → 侧栏里这是**对的**；
- **`%TEMP%` 临时夹具跑链** → 出现 `C--Users-...-Temp-relay-b17-e2e-...-repo` 这种目录 →
  侧栏里就是一堆「新项目」。

登记册是**用户级**的，不随夹具目录一起消失：夹具删了，条目还在 ⇒「新建了很多项目」。

**链接落点一直是对的**：ecclaw 的真链全部落在 `F--soft-00selfmade-ecclaw`，142 个 jsonl 的 cwd 均为
`F:\soft\00selfmade\ecclaw`。这不是「接错项目」，是「夹具的副作用被渲染成了项目」。

完整机制见同目录 `claude-project-registry.md`（本文只讲本批的处置与证据）。

## 2. 被否决的方案：`CLAUDE_CONFIG_DIR` 隔离（实测）

最直觉的办法是把 `CLAUDE_CONFIG_DIR` 指向临时目录，让夹具会话落在临时登记册里。
**实测失败**（`reports\iso-probe.ps1`，claude `999.0.0-local`）：

```
CLAUDE_EXIT=0                      # 构建根本没用这个变量
NEW_USER_PROJECT_DIRS=C--Users-Duanyi-AppData-Local-Temp-relay-iso-probe-20261127-103419-work
CFG_TREE_BEGIN
CFG_TREE_END                        # 临时配置目录里一个文件都没有
```

即：该构建仍写用户 profile 下的登记册。⇒ **隔离路线在当前构建上走不通**，
只能改成「跑完把条目挪走」。（探针真调了一次 claude：`session_id=7f013e2f-…`，`total_cost_usd=0.2543`。）

## 3. 装置改动

### 3.1 `relay-spawn.ps1`：新增 `-EphemeralWorkspace`

1. 起子进程**之前**快照所有候选登记册（`CLAUDE_CONFIG_DIR\projects` + **运行时推导**的 profile 下
   `.claude\projects`；两路 profile 来源：`HOMEDRIVE`+`HOMEPATH`、`ApplicationData` 上溯）；
2. 子进程跑完后，把**本次子进程新建的那一个**条目（键名 = 工作目录的 mangled 形式）从登记册挪到
   登记册旁边的 `_relay-ephemeral\<key>-<时间戳>\`；
3. **挪走而不是删掉**：会话转写仍在盘上（留证），只是不再被桌面端当成项目显示；
4. 快照里就有的条目 ⇒ **绝不碰**（真实项目目录不会被误伤）；
5. 挪出位置选在登记册**同级**：登记册与工作区常跨卷，跨卷不是「移动」。

**默认关闭**：真实项目**必须**继续出现在桌面端项目列表里，装置无权替用户隐藏真实项目。

### 3.2 `start-relay.ps1`：同名开关

带 `-EphemeralWorkspace` 起链时，写进 prompt 的 spawn 命令会带上该开关（`-Execute -AdoptLock
-EphemeralWorkspace`），于是**链上每一环**（子环自己再起下一环）都自动清理自己那条条目。

### 3.3 「代码里不许出现 home 字面量」门禁

第一版实现直接写了 `$env:USERPROFILE` / `$env:HOME`，触发 `kit_no_home_literals_in_code`（红）。
改为**运行时推导**（`HOMEDRIVE`+`HOMEPATH`、`ApplicationData` 上溯），并保留 `CLAUDE_CONFIG_DIR` 这一路。
本机实测：`HOMEDRIVE=C:`、`HOMEPATH=\Users\Duanyi`、`HOME`（空）、`APPDATA=C:\Users\Duanyi\AppData\Roaming`
⇒ 推导出的 profile = `C:\Users\Duanyi` ⇒ 登记册路径命中真实目录（29 个条目）。
门禁字面量扫描现为 **0 命中**（9 个装置文件全扫）。

## 4. 门禁：新增 case 27（鉴别力：好样本 / 坏样本各跑一次）

`scripts\selftest.ps1` case 27 用一个 PATH 优先的假 `claude.cmd` **真跑**起环驱动两遍：

| 样本 | 命令 | 期望 | 判据 |
|---|---|---|---|
| 坏样本 | 不带 `-EphemeralWorkspace` | 条目**留下**（否则下面的绿是假绿） | `ephemeral_entry_appears_without_the_switch` |
| 好样本 | 带 `-EphemeralWorkspace` | 条目**消失**、转写**留证**、别的登记册**不受影响** | `ephemeral_entry_is_gone_after_the_switch` / `ephemeral_transcript_is_kept_as_evidence` / `ephemeral_cleanup_touches_no_other_registry` |

另有 3 条启动器断言：带开关时 prompt 必须含 `-EphemeralWorkspace`、默认必须**不含**、安装器退出码为 0。

本批共 **10 条**新断言，全部 `CASE_PASS`。

## 5. 存量清理

`%USERPROFILE%\.claude\projects` 下的 16 个 relay 夹具条目 + 1 个探针条目已用**可恢复删除**
（`mavis-trash.cmd`）清出；其中误删的真实项目目录 `F--soft-00selfmade-agentask-relay` 已按原样恢复。
**注意**：必须用 `E:` 真实路径，`C:\Users\Duanyi\.claude` 是 junction，junction 路径会被回收站拒绝。
清理后登记册 29 个目录，全部对应真实项目。

**桌面端需要刷新或重启**才会不再显示那些条目 —— 它的列表是渲染时扫描目录得到的。

## 7. 坑

1. **`CLAUDE_CONFIG_DIR` 在本机构建上不生效** —— 隔离路线实测否决，别再设计第二遍；先查构建行为再定方案。
2. **`C:\Users\Duanyi\.claude` 是 junction → `E:\Users\Duanyi\.claude`**：回收站只认**真实路径**，
   用 junction 路径会被拒（报「路径不存在」/拒绝）。
3. **登记册与工作区常跨卷**：`Directory.Move` / `Move-Item` 跨卷不是移动 ⇒ 挪出位置必须在**登记册同级**。
4. **门禁「代码里不许出现 home 字面量」是硬项**：`$env:USERPROFILE` 也会命中（`-match` 大小写不敏感），
   正确写法是**运行时推导**（`HOMEDRIVE`+`HOMEPATH`、`ApplicationData` 上溯）。
5. **假绿防范**：case 27 必须先跑**不带开关**的坏样本，条目没留下就说明夹具根本没写登记册，
   此时好样本的「条目消失」毫无信息量。
6. **处置是「挪走」不是「删掉」**：转写留证，且真实项目的条目绝不能碰（快照里已有的 ⇒ 跳过）。
