# B20 小结：真链上的自动收尾端到端 + 触顶 HINT 口径修复

本批只补 B19 §9 遗留 3（「真链上自动收尾的端到端未做」），外加一处由此暴露的措辞缺陷。
B19 已把机制建好（`-AutoFinalize` + 自测 case 26），但那次只用了真实装置 + 真实台账 + 真子进程，
**没有**一条真实 `session_create` 起的链跑到触顶。本批补的就是这一条，判据不变：
盘上 `status` 回读 `status=done`，且 `current_stage > max_stages`。

---

## 1. 夹具与负向控制：`reports\b20-e2e-setup.ps1`

一次性 git 仓建在 `%TEMP%`，走真安装器（两遍）→ 真启动器起链：

- 安装第一遍 `ADAPTATION_STATUS=pending`，第二遍 `confirmed`（`applied=8/8`）—— 收编判据没被本批碰坏。
- 启动器 `exit=0`，`ledger_bootstrapped` + `prompt_written`；台账 `status=running current_stage=1 max_stages=1 stages=0`。
- **负向控制**（同一夹具、`-MaxStages 1`、不给任何阶段记录）：`exit=3`、
  `FAIL reason=chain_at_stage_cap current_stage=1 max_stages=1 stages=none all_done=unknown`、
  `HINT=stage_cap_reached_with_no_stage_records: ...`、**没有** `AUTO_FINALIZED`、台账仍 `running`。
  这一条是「算不出完成度就不许收尾」的鉴别力来源：`all_done=unknown` 时 `-AutoFinalize` 必须无所作为。
- 结果：`SETUP_EXIT=0`、`SUMMARY fail=0`、`SETUP_OK`（夹具根日志 `b20-setup.log` 7139 B、`b20-negative.log` 698 B）。

单环（`MaxStages=1`）是刻意选择：起链后即触顶，天然把「闸门顺序」也一起验了 ——
`stage_in_progress` → `chain_already_running` → 触顶，三段之后才轮到 `-AutoFinalize`。

## 2. 真链：一条真实 `session_create` 起的环跑到触顶

- `session_create` 只传 `agent_name` / `title` / `workspace_dir`（反斜杠绝对路径）/ `model` / `content`，
  **不传** `effort` / `defer_first_turn` / `parent_session_id`；建环后立刻回读。
  实测 `session_id=mvs_bbd188bdad554326b41db3872cb9754f`，模型 `minimax/MiniMax-M3`。
- 锁：`relay-lock.ps1 -Action adopt -SessionId <sid>` → `LOCK_ADOPTED holder=mvs_bbd188... stage=1`。
- 「末环不许自己翻终态」靠 **OPERATOR NOTE 前置注入 `content`** 实现，启动器生成的 prompt 原文逐字保留。
  子会话严格服从：写 `docs\relay\stage-1-inventory.md`（2969 B）+ 两个补丁文件，
  两次台账提交都走 `-Action status` → `-DryRun` → `-Action commit -ExpectSha256`，
  sha 链 `44295922...` → `28892D10...` → `29CB450E46AC43245BE835968A72A82146E876BADAFF4DF38B1E1F694FEBAD8A`；
  **没有** `set_status=done`、没有起下一环、没有释放锁。
- 于是盘上得到 crash shape：`status=running current_stage=2 max_stages=1 stages=[1:done] next_session_id=null`
  —— 正好是 `stop_conditions` 里「触顶且每阶段都 done 就该收尾」却没人收的那种。

## 3. 一次性验证器：`reports\b20-verify-finalize.ps1`

对上面那个 shape 按顺序验四件事：

1. `-DryRun` 不写盘（sha256 不变）且印 `DRYRUN skip=auto_finalize`；
2. `-AutoFinalize` 仍以 `exit 3` 结束（语义是「这次没起链」），印
   `AUTO_FINALIZED status=done before=<hex64> after=<hex64> path=<file>`，两个 sha 相异，并换上
   `HINT=chain_closed_by_auto_finalize: ...`，且**不**补第二条 `FAIL reason=chain_exhausted`；
3. 盘上回读 `status=done`、`updated_at` 前进、`next_session_id` 仍空；
4. 再跑一次必须 `reason=chain_exhausted` 而不是二次收尾，且台账字节不变。

- 验收那一次：`VERIFY_EXIT=0`、`SUMMARY fail=0`、`VERIFY_OK`，25 条检查全 PASS。
  逐项输出没有落成仓库文件，且夹具根的 `b20-verify.log` 已被后来的一次复跑覆盖 —— 见 §7 与 §10 坑 41。
- 夹具终态（本文件写成时仍可回读）：`docs\relay.json` 2366 B、
  sha256 `B62CEBF9D4708923EC49B6CC6E88050BCB0CF8811547522F64F886884EA08DEA`、
  `status=done current_stage=2 max_stages=1 stages=1:done next_session_id=null`。
- **本批改了这个脚本**：加陈旧状态守卫。它是一次性的（吃的就是上面那个 crash shape），
  可复跑时原来会印出 7 条 `FAIL`（`pre_crash_shape` / `pre_sha_matches_child` / `dry_status_running` /
  `fin_cap_reached` / `fin_autofinalized_line` …），读起来和产品回归一模一样。
  现在只要 `sha_before` 不等于期望的 pre-sha，就印
  `STALE_STATE fixture_no_longer_holds_the_crash_shape ... expected_pre_sha=29CB450E... status=done` +
  `HINT=one_shot_verifier: ...` + `SUMMARY fail=0 checks_run=0 refused_stale_state=true`，`exit 2`，**一个字节都不动**。
  实测（`reports\b20-verify-finalize.log`）：`VERIFY_EXIT=2`，同一份台账事后仍 `B62CEBF9...`。

## 4. 唯一产品改动：触顶 HINT 按 `-AutoFinalize` 二选一

`tool\templates\start-relay.ps1` 触顶闸门 `allDoneState=true` 分支（`:192-200`）此前**无论带不带**
`-AutoFinalize` 都印「Close the chain with relay-ledger.ps1 ..., then submit a patch {"set_status":"done"}」，
而同一运行又自己写 done —— 同一次输出里给了互相矛盾的两条指令。

- 改成按 `$AutoFinalize` 二选一：不带的保留手工补救措辞；带的说明「本次运行会经 `relay-ledger.ps1` 关环，
  `-DryRun` 只印 skip，写失败只 WARN，别靠抬 `-MaxStages` 续命」。
- **两处措辞共用同一机器 token** `HINT=all_stages_done_but_status_running:`（token 命名的是形态，不是补救动作）；
  自测按 token 断言，所以 `scripts\selftest.ps1` **一个字没改**。
- 另两个分支（`all_done=false` / `unknown`）未动。
- 硬不变式：`Copy-Item tool\templates\start-relay.ps1 device\start-relay.ps1 -Force`，两侧逐字一致。

### 4.1 改这行踩出来的自测红灯（重要）

第一版新措辞里直接引用了机器 token `AUTO_FINALIZED`。`-match` 大小写不敏感，
于是 dry-run 那一轮（本应「什么都没写」）的文本命中该 token，
`auto_finalize_dry_run_writes_nothing` 判红 —— **断言没错，是措辞把「写过盘」的机器证据提前泄漏给了没写盘的那一轮**。

修法是让措辞不引用任何 token（改成「the outcome line below says whether it wrote or was skipped by a dry run」），
而不是放宽 `selftest.ps1:1189` 附近的断言：那个 token 代表「启动器确实写过盘」，语义正确，动它才是把门禁改绿。

## 5. HINT 双跑见证：`reports\b20-hint-witness.ps1`

改 HINT 之后没有重跑真链（要再起一个真实会话，代价高且对该消息没有增量鉴别力），
改用**同形态双跑见证**：脚本内部先跑 §1 那套安装 + 起链 + 两次台账提交，
在**同一份台账**（`running/2/1/[1:done]`）上分别用「不带 flag」与「带 `-AutoFinalize`」各跑一次启动器。

复跑（`reports\b20-hint-witness.log`，夹具 `%TEMP%\relay-b20-e2e-20261126-224818`，head `c9f6483`）：

- 装机字节确认：`COPY start-relay.ps1 bytes=35754 sha16=753FBF3C03BB083E` —— 见证跑的是**最终字节**。
- `LAUNCHER_PLAIN exit=3` ⇒ `PASS plain_token_kept` / `plain_hand_close_advice` / `plain_no_finalize` / `plain_ledger_running`。
- `LAUNCHER_AUTOFINALIZE exit=3` ⇒ `AUTO_FINALIZED status=done before=A72FAEED... after=2ABAC79D...` +
  `HINT=chain_closed_by_auto_finalize: ...`，断言 `auto_no_hand_close_advice` / `auto_names_itself` /
  `auto_finalized` / `auto_hint_swapped` / `auto_ledger_done` 全 PASS。
- `PASS witness_hints_differ same state, flag decides the remedy` —— 两条判据在同一输入上给出不同建议，
  说明是 flag 在决定，不是环境抖动。

## 10. 本轮工具坑（接 B19 的 37）

38. **一次性验收器的失败模式必须和产品缺陷长得不一样**：`b20-verify-finalize.ps1` 复跑时对已被消耗的夹具
    印出 7 条 `FAIL`，和真回归无法区分。判据类脚本要么能重建前态，要么必须先验前态、不符就 `exit 2` 单独报
    `STALE_STATE`。**「复跑还能红」不是鉴别力，是判据在前态缺失时的自伤。**
39. **验收器的日志路径不能是「每次运行先删再写」的固定文件**：`$log = <fixture>\b20-verify.log` 在第一次跑
    覆盖了 setup 之后，第二次跑又把验收那次的逐项 PASS 行整份截断 —— 于是「验收记录」变成「复跑记录」。
    一次性脚本的日志要么带运行戳，要么写到只增不改的位置。
40. **`-match` 不区分大小写 ⇒ 给用户看的措辞里不能出现机器 token**：新 HINT 引用了 `AUTO_FINALIZED`，
    dry-run 那一轮文本命中它，`auto_finalize_dry_run_writes_nothing` 判红。token 是「确实写过盘」的证据，
    任何面向人的句子里出现它就是自证。修措辞，别改断言。
41. **`Set-Location` 与写盘放同一条内联命令会被本地安全策略拒**
    （`write/delete targets cannot be verified safely after a command working directory change`）。
    B19 坑 36 记过一次，本批又踩：`cd <repo>; ... *> <file>` → 直接 `Permission denied`。
    正确形状：不带 `cd`（会话工作目录本来就是仓库根）、全部用绝对路径。
42. **夹具里的台账如果从未进过 git，就没有「恢复前态」这条路**：本批想用 `git checkout <commit> -- docs/relay.json`
    把夹具退回收尾前，实测 `git status` 全是 `??`（安装器与启动器的产物都没提交）⇒ 恢复等于手写 JSON = 编造证据。
    想可重跑的夹具，必须把「前态」也提交一次，否则只能重建。
